## ۱. خواستهٔ مالک و شیوهٔ قطعی ادامه

هدف، نزدیک‌شدن به بالاترین سرعت ممکن **در کل سایت** هالیوس بدون تغییر یا خرابی طراحی، هویت بصری، خوانایی فارسی، انیمیشن‌های لازم، فرم، گزارش/موتور، فروشگاه، حساب، حریم خصوصی، آمار و SEO است. معیار پذیرش برای هر URL عمومی نماینده: **میانهٔ Lighthouse موبایل ≥۹۰ و دست‌کم ۴ نتیجهٔ ≥۹۰ از ۵ اجرای معتبر هم‌شرایط**؛ صفحات ساده هدف تکمیلی ۹۵–۱۰۰ دارند. اگر هدف محقق نشد، مورد باز است و فقط با پذیرش صریح مالک می‌تواند بسته شود.

**ترجیح قطعی مالک:** GitHub-first؛ کارهای واقعی و تغییرات باید در GitHub مدیریت شوند و در پایان نسخهٔ قابل دریافت/انتشار ارائه شود. مالک نمی‌خواهد پس از هر مرحله یک PowerShell، ZIP، نصب npm، Lighthouse دستی یا تصمیم خرد انجام دهد. مسئول انتخاب راه‌حل، یکپارچه‌سازی، شواهد و تست مجری است. کار را در برش‌های مفید تجمیع کن؛ از آزمایشگاه شخصی ویندوز مالک به‌عنوان محل کشف فرضیات خام استفاده نکن. اگر چت Work به مرورگر/کامپیوتر آزمایشی مستقل دسترسی دارد، همان را به‌کار ببر؛ اما **GitHub به‌تنهایی اجرای مرورگر یا Build را اثبات نمی‌کند**.

**قانون انتشار:** در مراحل ۰ تا ۶ به‌صورت پیش‌فرض **هیچ commit/tag/push میانی برای کد و هیچ deploy** انجام نشود؛ موارد مستقل مجاز پیش بروند، کاندیدای معتبر حفظ شود، و فقط پس از گزارش کامل و تأیید صریح مالک، مرز انتشار مرحلهٔ ۷ اجرا شود. انتشار VPS فقط با موتور رسمی `ops/vps/halleus-release.sh`، پس از بررسی خود اسکریپت و وضعیت واقعی تولید. صرف `git pull` روی سرور، فعال‌شدن نسخهٔ سایت را اثبات نمی‌کند. **هیچ GitHub Actions، PR آزمایشی، توسعهٔ زیرساخت اضافی، ZIP اجرایی یا کار خارج از همین رودمپ** مگر درخواست مستقل مالک.

## ۸. مسیر اجراییِ واضح برای چت جدید (بدون درخواست تصمیم‌های خرد)

**R0 — بازیابی وضعیت و safety:** سورس واقعی GitHub و فایل‌های authority را بخوان؛ HEAD، origin، main، allowed files، کاندیدا و وضعیت دقیق محیط مستقل خودت را بررسی کن. چون این سند با commit مستندات ثبت می‌شود، SHA جدید `main` ممکن است متفاوت باشد؛ **کد مبنا همچنان `d4dcbb7...` است و تفاوتِ docs-only نباید با تغییر کد اشتباه شود**. محل C روی سیستم مالک فقط گزارش‌شده است؛ در محیط مستقل آن را از منبع واقعی و patch تأییدشده بازسازی کن. از پاک‌کردن تغییرات معتبر مالک بپرهیز.

**R1 — تکمیل مرحلهٔ ۱ و ۲ با کمترین تکرار:** کاندیدای سالم CSS را حفظ کن. ابتدا بررسی ظرفیت و پایداری CPU/Chrome/Next در یک آزمایشگاه مستقل؛ A/C را ترجیحاً روی همان پورت و **به‌صورت متوالی**، در پروفایل و data ثابت، با سرور و مرورگر جداگانه اجرا کن. دست‌کم سه اجرای معتبر screening، بعد پنج اجرای متناوب برای پذیرش. پاسخ نامعتبر/timeout مستقلِ مرورگر را از regression کد جدا کن. اگر لازم بود، تغییر Analytics و Form+Picker را با دو variant جدا، اما با CSS ثابت و گارد اثرگذار مقایسه کن. Trace را به تابع/chunk و Layout واقعی نسبت بده. همراه آن هندسهٔ ۳۲۰/۳۶۰/۳۹۰/۴۱۲/۴۳۰/۷۶۸/۱۲۸۰/۱۴۴۰، چاپ، لنگر، touch/keyboard، شهر/ریتری و خطای console/hydration را بررسی کن.

**R2 — انتخاب اصلاحات و تکمیل مراحل ۳ و ۴:** فقط bottleneck ثابت‌شده را اصلاح کن؛ تغییرات مرتبط را در یک candidate منطقی جمع کن، نه micro-batch. فرضیهٔ بی‌اثر یا مضر را کنار بگذار، اما کاندیدای معتبر را reset نکن. سطح دشواری/اثر/گارد هر برش را مشخص کن. برای Compare lazy auth و کار مشترک shell، تأثیر واقعی JS/interaction را پیش/پس اندازه بگیر.

**R3 — تکمیل مراحل ۵ و ۶:** با حساب/گزارش/قیمت/پرداخت کاملاً مصنوعی و مرز DB self-hosted صحیح، عملکرد و قرارداد را تست کن. موارد غیرقابل اجرا فقط `EXTERNAL_BLOCK` یا `BLOCKED_BY_DEPENDENCY`، نه PASS. یک اجرای first-run failure discovery تمام چک‌های مستقل را ادامه دهد و تمام علت‌های مرتبط را با هم جمع کند؛ `SAFETY_FATAL` فقط برای repo/branch/HEAD/worktree/out-of-scope/destructive risk. R2 اصلاح و resume از state معتبر، نه از صفر. نتایج پنج‌تایی هر URL، مدیان، LCP/FCP/TBT/CLS، سفرهای حساس و desktop را ثبت کن. اثر روی production/migrations را گزارش بده.

**R4 — مرز انتشار فقط با تأیید:** فایل‌های تغییرکرده، diff، guardهای PASS/FAIL/BLOCKED، نتایج واقعی قبل/بعد و اثر تولید را نشان بده. بدون درخواست و تأیید مجزا برای مرحلهٔ ۷ **commit/tag/push/deploy کد نکن**. پس از approval، commit/tag/push نهایی و deployment فقط از `ops/vps/halleus-release.sh` با current/previous و service/smoke. برای release صرفاً سرعت، رفتار گزینهٔ `--skip-wiki-maintenance` در نسخهٔ اسکریپت واقعی بررسی شود. rollback رسمی در صورت خطا. `ROADMAP_COMPLETE` فقط بعد از اتمام تمام موارد active، از جمله release اگر جزو roadmap است.

**اگر Work محیط مرورگر/ساخت مستقل ندارد:** آن dependency را صریح ثبت و سایر تحلیل‌ها/اصلاحات مستقل را ادامه بده؛ از مالک نصب npm، گردش طولانی PowerShell، ارسال ZIP، تکرار یک سؤال پاسخ‌داده‌شده یا انتشار کاندیدای سنجش‌نشده نخواه. فقط درخواست حداقلی و یک‌جای واقعاً ضروری مجاز است. در هیچ صورت **«زمان‌بندی آینده»، نتیجهٔ ساختگی یا PASS بدون شواهد** ننویس.

## ۹. چیزهایی که هنوز انجام **نشده‌اند**

- هیچ بهینه‌سازی جدیدی برای سرعت **به‌طور معتبر پذیرفته نشده**؛ فقط اصلاح اولیهٔ ظاهر چارت C در local.
- نه کد C در GitHub main ذخیره شده، نه تغییر draft مربوط به Compare اعمال شده، نه variantهای Analytics/Form+Picker build/test شده‌اند.
- پنج اجرای Lighthouse معتبر هم‌شرایط برای همهٔ URLهای عمومی انجام نشده. نتیجهٔ ۳۸ C هشدار ناقص‌بودن دارد؛ هدف ≥۹۰ هیچ مسیری بسته نشده.
- سفرهای کامل فرم/چرخ/حساب/گزارش/سبد/پرداخت و cross-viewport/desktop/print تست یکپارچه نشده‌اند.
- هیچ دیتابیس تولیدی، سرویس VPS، release symlink، GitHub Actions یا تنظیمات تولید تغییر داده نشده است؛ **مرحلهٔ ۷ هنوز مجوز ندارد**.
- سند حاضر **فقط ذخیرهٔ وضعیت و نقطهٔ ادامه** است؛ از وجود آن تکمیل فنی یا انتشار استنباط نشود.

## ۱۰. خلاصهٔ handoff در یک پاراگراف

مالک می‌خواهد ChatGPT Work/چت اجرایی، با خواندن رودمپ و این سند، تمام مراحل مجاز ۰–۶ را خودش به‌صورت GitHub-first و با کمترین دخالت مالک انجام دهد؛ کاندیدای C محلی شامل حذف containment مشکل‌ساز موبایل چارت و اصلاح گارد است اما هنوز در GitHub code committed نیست. A/B/C production build موفق داشته‌اند و fixture محلی PostgreSQL و baseline شبکه/asset ثبت شده است. A در Lighthouse 49 و C در یک اجرای ناقص 38 شده؛ علت هنوز تفکیک نشده و نباید انتشار داد. باید ابتدا اختلاف مرورگر/ابزار و سه تغییر Analytics/Form/Picker را به‌صورت کنترل‌شده ایزوله کرد، سپس گلوگاه‌های واقعی مشترک و خانواده‌ها را اصلاح و با تست قابل تکرار پذیرفت. هیچ micro-step یا ZIP تحمیل نشود. فقط **پس از پایان مراحل ۰–۶ و تأیید جداگانهٔ مالک** مرحلهٔ انتشار نهایی GitHub/VPS مجاز است.
